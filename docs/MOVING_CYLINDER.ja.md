# 可動気筒のガス交換

[English](MOVING_CYLINDER.md) · [简体中文](MOVING_CYLINDER.zh-CN.md) · [Français](MOVING_CYLINDER.fr.md) · [Русский](MOVING_CYLINDER.ru.md) · **日本語** · [한국어](MOVING_CYLINDER.ko.md) · [Deutsch](MOVING_CYLINDER.de.md) · [Español](MOVING_CYLINDER.es.md) · [Italiano](MOVING_CYLINDER.it.md) · [Português](MOVING_CYLINDER.pt-BR.md)

`gas_cylinder` は、一つの回転クランクを一つのガスチャンバーへ接続します。密閉断熱ベンチマークとは異なり、このチャンバーは独立した質量と内部エネルギーを持つため、絞りと壁面リンクが状態を変えられ、圧力がクランクを駆動します。コンポーネントは Core、JSON、CLI、MCP、移植可能アセットから使えます。ピストン慣性や詳細な化学はモデル化しません。別の[予混合燃焼](PREMIXED_COMBUSTION.ja.md)と[クランク角タイミング](VALVE_TIMING.ja.md)のコンポーネントが、燃料エネルギーの変換を供給し、接続された絞りを制御します。

## モデル契約

```csharp
var definition = new ModelDefinition
{
    StepNanoseconds = 50_000,
    Nodes = [NodeDefinition.Rotor(1, 0.2, 60),
        NodeDefinition.CylinderGas(2, 100_000, 300),
        NodeDefinition.Thermal(3, 500, 350)],
    Components = [ComponentDefinition.GasCylinder(10, 1, 2, new()
    {
        Bore = new(86, Unit.Millimeter), Stroke = new(86, Unit.Millimeter),
        RodLength = new(143, Unit.Millimeter), Phase = new(0, Unit.Radian),
        CompressionRatio = 10, BackPressure = new(1, Unit.Bar)
    }), ComponentDefinition.GasReservoir(11, 2, 50e-6, 110_000, 300, 0.8, 100, 1),
        ComponentDefinition.GasHeatLink(12, 2, 3, 2.5)]
};
```

ガスノードは、初期の絶対圧力、温度、R、ガンマを供給します。その `Storage` 量はゼロ/None です。容積を所有するのは、ちょうど一つの気筒コンポーネントです。コンパイラは、位相を含め、クランクの初期角度における幾何から初期質量とエネルギーを導出します。独立に指定された容積、または一つのチャンバーに対する二人の気筒所有者は拒否します。接続されていない固定ガスノードは、引き続き正の明示的な容積を必要とします。

JSON では、可動チャンバーに `domain: "gas"` を使い、`storage` を省きます。`gas_cylinder` コンポーネントは、`node_a`（回転）、`node_b`（ガス）、およびパラメーター `bore`、`stroke`、`rod_length`、`phase`、`compression_ratio`、`back_pressure` を必要とします。組成や初期ガス状態は、このコンポーネントに重複して置きません。ガスノードは圧力、温度、質量、内部エネルギーを公開します。気筒は容積、ピストン変位、クランクトルクを公開します。ポート、絞り、開度の境界、壁面リンクは、既存の[ガスネットワーク契約](GAS_NETWORK.ja.md)を使います。

タイミング付き絞りも予混合追跡もない可動チャンバーを含むモデルは、忠実度 `moving_cylinder_gas_exchange` を報告し、ソルバーフィンガープリントタグ 5 を加えます。既存の線形、密閉気筒、定容だけのモデルは、フィンガープリントとステッピングを保ちます。組成は固定のままで、接続されたガスノードは一致しなければならず、すべてのパラメーターは `unverified` のままです。

## 方程式と保存的な結合

組成が固定された熱量的完全気体について:

```text
p = (gamma - 1) U / V(theta)
T = U / (m cv)
dm/dt = sum(inflow) - sum(outflow)
dU/dt = -p dV/dt + Q_wall + sum(mdot_in h_in) - sum(mdot_out h_out)
tau_gas = (p - p_back) dV/dtheta
```

質量/エネルギーの収支は、開いた系の標準的な熱力学第一法則に従います。[Cantera の制御体積方程式](https://www.cantera.org/stable/reference/reactors/controlreactor.html)を参照してください。その参照が支えるのは方程式であり、Power! の積分手法や検証ではありません。ガスは、Cantera の線形で一方向のバルブ実装ではなく、既存の双方向圧縮性ノズル則を使います。背圧仕事は外部源仕事です。リザーバーエンタルピーと壁面交換は、既存の台帳符号を保ちます。

実装は、可動チャンバーを含むモデルに対称な作用素分割を使います。

1. 開始時のクランク幾何で、ガス交換と壁面熱を半ティック進めます。
2. 有界な離散勾配のクランクソルバーで、連成した電気機械と断熱圧力仕事を全ティック解きます。
3. 結果のクランク幾何で、ガス交換と壁面熱を半ティック進めます。
4. 蓄積されたガス壁面熱と電気機械損失を、熱求解へ適用します。

手順 2 の間、質量は固定され、`U_new = U_old (V_old/V_new)^(gamma-1)` です。平均ガス圧力とトルクは、この同じエネルギー変化の差分商から得ます。クランクはガス仕事から背圧仕事を引いたものを得ます。チャンバーは、対応するガス仕事を浮動小数点精度でちょうど失います。`log1p`/`expm1` と解析的な体積の差分商が、小さな刻みと死点のまわりで、ほぼ等しい状態同士の引き算を避けます。複数の気筒は、クランクを共有するか、連成したシャフトを通して作用できます。

この分割は、壁面伝達のない、テストされた滑らかなチョーク流の事例について 2 次収束します。壁温度は両方のガス半ステップの間固定され、その後に既存の熱求解が続きます。壁結合の精度は 1 次のままです。平衡付近の流量リミッタも、局所次数を変え得ます。保存は精度を確立しません。

## 境界、失敗、互換性

クランク移動量はティックあたり 0.25 rad までに制限されます。非線形求解は最大 16 反復、直線探索は 10 回です。各ガス半ステップは、4096 サブステップの上限、2% の目標相対変化、25% の修正後変化による拒否を保ちます。無効または非有限なガス状態、出力、あるいはソルバーの枯渇は、先行するすべてのティックとスケジュールされた入力を含む、呼び出し側バッチ全体を拒否します。再試行する前に `step_ns` を減らし、流路面積、ガス状態、コンダクタンス、クランク速度、慣性を調べてください。キャンセルと分岐は、すべてのガス状態と台帳状態を保持します。成功したステッピングと、呼び出し側バッファへのスナップショットは、マネージドメモリを割り当てません。

アセット v4 は、各ガス気筒に有界な索引付き幾何レコードを加え、v1/v2/v3 リーダーをすべて保持します。ソルバー作業領域を直列化することはありません。本物の定容 v3 フィクスチャが、可動幾何の導入が以前のガスフィンガープリントやリプレイを変えないことを検証します。[アセット形式](ASSET_FORMAT.ja.md)と[フィクスチャの来歴](../tests/Power.Tests/Fixtures/README.md)を参照してください。

## 実験とエビデンス

[可動気筒のラボラトリー](../assets/labs/moving-cylinder.power.json)は、二つのリザーバー絞りと有限な熱壁で、一つの気筒をモータリングします。8 つの時間ベースの開度イベントが、チャンバーへの流入と流出を動かし、レポート境界と表示境界の間のティックを含みます。これはキャリブレーションされていないモータリング実験です。スケジュールは ECU、カムプロファイル、4 ストロークエンジン制御、燃焼モデルではありません。

テストは、閉じたチャンバーを既存の密閉気筒実装と、正転/逆転および死点を通して比較し、開いたチャンバーを支配 ODE の独立に書かれた RK4 積分と比較します。後者は、幾何、チョーク質量流量、圧力仕事を方程式から直接書き下します。刻みの細分化は、滑らかな流れと壁結合の精度を別々に検査します。追加の検査は、複数の連成/共有クランク、密閉/開放が混在する気筒、保存、不正な所有、単位の正規化、アトミックな失敗/回復、分岐、キャンセル、ゼロ割り当て、移植可能な互換性、すべての JSON/MCP/アセットのレポート境界をカバーします。

Unity には、動くピストン表示、ガス接続、インポート/Play テストが含まれます。実際のエディター、レンダリング、Play Mode、IL2CPP のエビデンスは、まだ未着手です。実行された検査は[検証記録](VALIDATION.ja.md)、残るエンジン、トランスミッション、制御、キャリブレーション作業は[ロードマップ](ROADMAP.ja.md)を参照してください。
