# Frontière Zig native

[English](NATIVE_ZIG.md) · [简体中文](NATIVE_ZIG.zh-CN.md) · **Français** · [Русский](NATIVE_ZIG.ru.md) · [日本語](NATIVE_ZIG.ja.md) · [한국어](NATIVE_ZIG.ko.md) · [Deutsch](NATIVE_ZIG.de.md) · [Español](NATIVE_ZIG.es.md) · [Italiano](NATIVE_ZIG.it.md) · [Português](NATIVE_ZIG.pt-BR.md)

Le propriétaire a repris la migration de langage natif le 2026-09-10. Les prototypes natifs sous `legacy/native` ont été migrés vers Zig, y compris leurs tests et leurs hôtes. Ils restent un runtime de recherche séparé : `Power.Core` et `Power.Assets` conservent leurs contrats managés sans dépendance et leurs doubles cibles, et Unity continue de charger les assemblys managés.

## Interopérabilité

La bibliothèque partagée native conserve le point d'entrée versionné `pwr_get_api`, les champs scalaires à largeur fixe, les tailles de structure, le temps entier en nanosecondes, les handles de génération, les tampons d'instantané appartenant à l'appelant et la table de fonctions. Les déclarations Zig `extern struct` et les conventions d'appel `.c` expriment l'ABI binaire existante ; elles n'exigent ni source ni en-têtes C dans ce dépôt. Le lanceur d'expérience P/Invoke C# dans l'outil de build .NET reste un consommateur de cette frontière. Les prototypes natifs de moteur, d'échappement et de transmission restent des API Zig internes, plutôt que d'être ajoutés en silence au schéma de modèle managé ou aux capacités natives publiques.

La migration doit conserver les équations, les limites de modèle, les ID stables, les diagnostics, le rollback de lot, les registres d'énergie et de masse, et les scénarios de régression. La fidélité des prototypes natifs et la calibration d'échantillon `unverified` sont inchangées. La vérification native est séparée des preuves réelles d'Unity Editor, de Play Mode et d'IL2CPP, et de l'achèvement de l'objectif de groupe motopropulseur complet.

## Provenance

L'implémentation C d'origine est récupérable depuis le commit Git `c342d4c05c9d0b14cae0ce1a85e3f2100dfd7bb3`. Les chemins et les hachages de ses fichiers source sont enregistrés dans `legacy/native/migration-manifest.json`. Le port Zig conserve les avis de droit d'auteur d'origine et la GPL-3.0-or-later avec l'exception de liaison Unity. Les documents historiques de conception et de recherche conservent leurs citations d'origine ; leurs descriptions de l'ère C ne décrivent pas la nouvelle construction.

Le lanceur LuaInstaller inutilisé et le README de son empaquetage ont été retirés le 2026-09-11. Leurs chemins et hachages d'origine figurent dans le même manifeste et renvoient à la même révision source. Le lanceur dépendait d'un pont `power_native` non implémenté et n'a jamais fait partie d'une construction fonctionnelle. Les opérations actuelles de CLI et de modèle utilisent les hôtes C#/JSON et Zig existants, plus l'hôte ABI P/Invoke de l'outil de build C#. Les propositions Lua dans les documents historiques sont des enregistrements de provenance, pas des dépendances ni des exigences d'implémentation actuelles.

## Construction et maintenance

Le compilateur est épinglé à Zig 0.15.2 dans `.zig-version`. La commande `install-zig` de l'outil de build (dans `tools/Build.cs`) utilise les [métadonnées de téléchargement Zig](https://ziglang.org/download/index.json) officielles, avec les hachages d'archive par plateforme commités. La construction n'a besoin ni d'un traducteur C, ni d'en-têtes, ni de CMake, ni d'une compilation de sources C. Linux n'a pas besoin de libc ; macOS utilise le `libSystem` fourni par l'OS. Le port a d'abord été traduit une fois, puis scindé en modules Zig maintenus avec des dispositions binaires partagées. La mémoire, les fonctions mathématiques et les opérations atomiques utilisent Zig et les API de l'OS de la plateforme. Les contrôles de sûreté restent activés dans les builds ReleaseSafe.

Les sources Zig utilisent des checkouts LF sur chaque plateforme. Sous macOS, l'outillage de vérification désactive la découverte du SDK Apple uniquement dans ses sous-processus de build Zig, en définissant `DEVELOPER_DIR=/dev/null`. Cela sélectionne les stubs d'éditeur de liens Darwin fournis avec Zig et évite l'[incompatibilité de Zig 0.15.2 avec Xcode 26.4 et les SDK plus récents](https://github.com/ghostty-org/ghostty/issues/11991), dont le stub `libSystem` utilise des cibles arm64e. La sélection Xcode du système est inchangée ; ces cibles natives n'ont pas besoin des frameworks Apple ni des en-têtes de SDK.

`dotnet run --file tools/Build.cs -- verify` exécute la vérification managée, puis la vérification native en série. `native-verify` n'exécute que la partie native. L'implémentation de `native-verify` (dans `tools/Build.cs`) rejette les sources et en-têtes C/C++ ainsi que le code source, le bytecode et les paquets Lua. Elle contrôle l'épingle du compilateur et le formatage, construit la bibliothèque et les deux hôtes Zig, exécute les suites Zig et la suite hôte ABI P/Invoke C#, et compare l'expérience électrothermique à sa fixture de référence C d'origine. Sous Linux, elle vérifie aussi que seul `pwr_get_api` est exporté publiquement et que la bibliothèque n'a aucun symbole externe non résolu.

La comparaison de référence conserve les empreintes de modèle, les unités, les correspondances de canaux, 11 instants d'échantillon et les valeurs physiques. Les valeurs entre chaînes d'outils utilisent des tolérances absolues/relatives explicites ; les hachages de rejeu doivent correspondre au sein du même binaire. Les rapports sous `artifacts/reports` distinguent l'exécution, les résultats de KPI/rejeu et la calibration non vérifiée. Les caches de compilateur ignorés et les checkouts de référence tiers privés ne sont pas des sources du dépôt.

## Corrections des tests d'archive

Trois anciens points d'entrée de test renvoyaient zéro même lorsque leur macro `CHECK` échouait. Le port propage ces échecs. La suite moteur s'arrêtait auparavant sur un échec caché, parce que son échantillon final de charge 22 Nm pouvait se trouver en coupure carburant du limiteur de régime. Ce scénario est conservé comme test explicite du limiteur ; la combustion continue utilise une charge d'essai synthétique de 32 Nm. La comparaison de contre-pression part maintenant d'un état de fonctionnement partagé et vérifie l'incrément analytique de couple de pompage avant de comparer la vitesse, ce qui évite la confusion entre démarrage et calage. Aucune équation moteur ni aucune valeur de calibration de production n'a été changée. La couverture de groupe motopropulseur automatique exerce maintenant aussi le rejeu, l'énergie différentielle, le brown-out et le rollback ; l'ancienne construction CMake omettait ce module entier.
